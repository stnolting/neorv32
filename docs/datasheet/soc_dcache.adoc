==== Data Cache (dCache)

[cols="<3,<3,<4"]
[grid="none"]
|=======================
| Hardware source files:  | neorv32_cache.vhd     | generic cache module
|                         | neorv32_cache_ram.vhd | tag and data RAM
| Software driver files:  | none                  |
| Top entity ports:       | none                  |
| Configuration generics: | `DCACHE_EN`           | implement CPU-exclusive data cache (D$) when `true`
|                         | `DCACHE_NUM_BLOCKS`   | number of cache blocks ("cache lines"); has to be a power of two
|                         | `CACHE_BLOCK_SIZE`    | size of a cache block in bytes (global configuration for I$ and D$); has to be a power of two, min 4
|                         | `CACHE_BURSTS_EN`     | enable burst transfers for cache update
|                         | `CACHE_UC_BASE`       | base address of uncached address space; has to be 256MB-aligned
| CPU interrupts:         | none                  |
|=======================

**Key Features**

* Direct-mapped, write-back and write-allocate
* Configurable number of blocks and block size
* Bypass for uncached and atomic accesses
* Synchronization via `fence` (`r`/`w` bits)
* Tag and data RAM mapped to memory primitives


**Overview**

The optional data cache (d-cache) is directly connected to the <<_cpu_loadstore_unit>> and is transparent
to software. It is enabled by the `DCACHE_EN` generic. Its size in bytes is `DCACHE_NUM_BLOCKS x CACHE_BLOCK_SIZE`.
Note that `CACHE_BLOCK_SIZE` is global for all caches. In a <<_dual_core_configuration>>, each core has a
private d-cache.

If `CACHE_BURSTS_EN` is enabled, all cache block transfers are executed as <<_locked_bus_accesses_and_bursts,**burst transfers**>>.
All devices reachable through the cache (including the <<_processor_external_bus_interface_xbus>>) must support bursts.
Accesses to the uncached address space (from `CACHE_UC_BASE` to `0xFFFFFFFF`, 256MB granularity, see <<_address_space>>)
**bypass the cache**. Atomic memory operations also bypass the cache. If the address is cached, a modified line is
written back first and then invalidated (see <<_memory_coherence>>).

.Tracking Cache Misses
[TIP]
Cache misses can be tracked by the CPU's <<_hardware_performance_monitors_hpm_csrs>>.

.Retrieve Cache Configuration by Software
[TIP]
Software can retrieve the cache layout from the <<_sysinfo_cache_configuration>> register.

.Memory Primitives
[TIP]
The tag and data RAM is encapsulated in `neorv32_cache_ram.vhd` and can be replaced by technology-specific IP.


**Cache Synchronization**

A `fence` synchronizes the d-cache by sweeping over all blocks:

* `w`: Dirty blocks are written back. They stay valid and become clean.
* `r`: Clean blocks are invalidated. Dirty blocks are kept.
* `r` and `w`: Dirty blocks are written back and all blocks are invalidated.

`fence.i` writes back all dirty blocks (like `fence w`). The CPU stalls until the synchronization has completed.
See <<_memory_coherence>> for more information.


**Cache Bus Error Handling**

[start=1]
. **Cache Bypass**: The bus error is reported to the CPU _immediately_ and with _full precision_. The address
in <<_mtval>> is the exact address that caused the error.
. **Cache Miss Without Eviction**: If a bus error occurs during the block fetch, the entire block is discarded and
the error is reported _immediately_ with _partial precision_. The address in <<_mtval>> lies within the block whose
fetch failed.
. **Cache Miss With Eviction**: If a bus error occurs while writing back a dirty block, the block is discarded and the
error is reported _immediately_ and _imprecisely_. The address in <<_mtval>> lies within the requested block, not
within the block that was written back.

.Bus Errors During Cache Write-Back
[IMPORTANT]
Write-back errors are hard to debug and might be fatal in machine mode. A future version will provide
the exact address of this type of error.

. **Cache Synchronization**: If a write-back fails during a `fence`, the block remains valid and dirty,
the synchronization continues, and the error is **not** reported to the CPU. The `fence` completes normally.
The error becomes visible later as an imprecise bus error when the block is evicted.
