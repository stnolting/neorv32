**Key Features**

* Philips(R) I²C(TM)-compatible host controller
* Configurable data/command FIFOs
* Programmable clock speed with clock stretching
* 7-bit or 10-bit addressing (handled by software)
* No multi-controller support; single host only


**Overview**

The NEORV32 TWI implements a simple I²C-compatible host controller to communicate with arbitrary I²C devices.
The TWI Controller supports only simple, basic operations: Generate START, REPEATED-START or STOP conditions,
transmit a byte and sample ACK/NACK and receive a byte sending ACK/NACK. The software can build on this foundation
to create more complex operations. Note that multi-controller mode and bus arbitration are not supported.

.Host-Mode Only
[IMPORTANT]
The NEORV32 TWI controller only supports **host mode**. Transmission are initiated by the processor's
TWI controller only. If you are looking for a _device-mode_ module (transactions initiated by an
external host) check out the <<_two_wire_serial_device_controller_twd>>.

The TWI controller provides two memory-mapped registers that are used for configuration & status check (`CTRL`)
and for transmitting/receiving data via the bus. The data and command register `DCMD` is transparently buffered
by separate RX and TX FIFOs. The size of these FIFOs is configured by the `IO_TWI_FIFO` generic. Software can
determine the configured FIFO size via the control register's `TWI_CTRL_FIFO_*` bits. The current status of the
RX and TX FIFO can be polled using the `TWI_CTRL_TX_FULL` and `TWI_CTRL_RX_AVAIL` control register flags flags.

The module is globally enabled by setting the control register's `TWI_CTRL_EN` bit. Clearing this bit will
disable and reset the entire module also clearing the internal FIFOs.


**TWI Bus Clock**

The TWI bus clock frequency is programmed by two bit-fields in the control register `CTRL`: a 3-bit clock
prescaler select (`TWI_CTRL_PRSCx`) is used for a coarse clock configuration while a 4-bit clock divider
(`TWI_CTRL_CDIVx`) is used for a fine clock configuration.

.TWI Prescaler Select
[cols="<4,^1,^1,^1,^1,^1,^1,^1,^1"]
[options="header",grid="rows"]
|=======================
| **`TWI_CTRL_PRSC[2:0]`**    | `0b000` | `0b001` | `0b010` | `0b011` | `0b100` | `0b101` | `0b110` | `0b111`
| Resulting `clock_prescaler` |       2 |       4 |       8 |      64 |     128 |    1024 |    2048 |    4096
|=======================

Based on the clock configuration, the actual TWI bus clock frequency f~SCL~ is derived
from the processor's main clock f~main~ according to the following equation:

****
_**f~SCL~**_ = _f~main~_ / (4 * `clock_prescaler` * (1 + `TWI_CTRL_CDIV`))
****

The maximum TWI bus clock is f~main~ / 8 and the lowest TWI bus clock is f~main~ / 262144. The generated
TWI clock is always symmetric having a duty cycle of exactly 50%. An accessed peripheral can slow down or
even halt the controller's bus clock by using **clock stretching** (= actively keeping the SCL line low).


**TWI Operations**

All I²C operations are controlled via the DCMD register and the FIFOs that operate transparently behind it.
Every write operation to the `DCMD` register writes to the TX FIFO; every read operation to the register
reads from the RX FIFO. The TX FIFO receives commands for individual bus operations as well as data to be
sent to the bus. The RX FIFO, on the other hand, receives only the data read from the bus via commands.

.List of Supported TWI Controller Operations
[cols="<3,<3,<5"]
[options="header",grid="all"]
|=======================
| Data written to `DCMD` / TX FIFO (C-macro in brackets) | Data pushed to RX FIFO | Description
| `100000000` (`TWI_DCMD_START`)  | -                           | generate (repeated) START condition
| `100000001` (`TWI_DCMD_STOP`)   | -                           | generate STOP condition
| `100000010` (`TWI_DCMD_RXACK`)  | -                           | receive 8-bit from bus and send ACK
| `100000011` (`TWI_DCMD_RXNACK`) | data read received from bus | receive 8-bit from bus and send NACK
| `0dddddddd` (`TWI_DCMD_TX`)     | data read received from bus | transmit 8-bit (`dddddddd`) to bus and sample ACK/NACK
|=======================

Depending on the configured FIFO size, complete I²C transactions can be programmed using DCMD. The TWI bus
engine automatically begins processing the commands as soon as the TX FIFO contains at least one element.
Software can use the `TWI_CTRL_TX_FULL` flag to check whether the TX FIFO is full. The `TWI_CTRL_RX_AVAIL`
flag can be used to check whether received data is available in the RX FIFO.

.FIFO Overflow
[WARNING]
There is no hardware-based monitoring for FIFO overflows. Make sure to check the
FIFO status flags before performing software-based FIFO (`DCMD`) read/write operations.

The control register's busy flag `TWI_CTRL_BUSY` is set as long as the TX FIFO contains data (i.e. programmed
TWI operations that have not been executed yet) or if the internal bus engine is still processing an operation.
An active transmission can be terminated at any time by disabling the TWI module. This will also clear all FIFOs.

in the 9th clock cycle of a data transmission (`TWI_DCMD_TX` command) the NACK/ACK bit of the accessed device is
sampled by the bus engine. If the controller receives a NACK, the following occurs:

* The current I²C transaction is automatically terminated by a STOP condition.
* The TX FIFO is completely flushed.
* The `TWI_CTRL_NACK` flag in the control register is set.
* Bytes already received in the RX FIFO are retained.

As long as the `TWI_CTRL_NACK` flag is set, no new commands can be written to the TX FIFO and the I²C bus
engine will not access the bus at all. The software has to explicitly clear the NACK flag (by writing a
`1` to the `TWI_CTRL_NACK_CLR` bit) before any new bus operations can be programmed or executed.

.Current Bus State
[NOTE]
The current state of the I²C bus can be checked using the read-only control register flags:
The `TWI_CTRL_SENSE_SCL` and `TWI_CTRL_SENSE_SDA` flags indicate the electrical level of the respective
bus line. The `TWI_CTRL_CLAIMED` flag indicates whether the TWI controller currently has bus access; it
is set while generating a START condition and cleared after generating a STOP condition.

Note that STOP conditions can only be generated if the I²C bus is actually claimed by the TWI controller
(the `TWI_CTRL_CLAIMED` flag is set). If the bus is not claimed by the TWI controller, any programmed
STOP condition commands are silently discarded.


**TWI Interrupt**

The TWI controller provides a single interrupt request that indicates the completion of a programmed command
sequence. The interrupt request becomes active as soon as the TX FIFO becomes empty and the internal bus engine
completes the last command. The interrupt is therefore also triggered if a NACK is received during a data
transmission (since the TX FIFO is then automatically cleared; see above). The software has to acknowledge the
interrupt request by writing a `1` to the `TWI_CTRL_IRQ_CLR` bit  to clear the interrupt request again.


**Tristate Drivers**

The TWI controller requires two tristate drivers (actually: open-drain drivers - signals can only be actively
driven low) for the SDA and SCL bus lines. These drivers have to be implemented by the user in the setup's top
module / IO ring. A generic VHDL example is shown below (here, `sda_io` and `scl_io` are the actual I²C bus
lines, which are of type `std_logic`).

.TWI Tristate Driver Example (VHDL)
[source,VHDL]
----
sda_io    <= '0' when (twi_sda_o = '0') else 'Z'; -- drive
scl_io    <= '0' when (twi_scl_o = '0') else 'Z'; -- drive
twi_sda_i <= std_ulogic(sda_io); -- sense
twi_scl_i <= std_ulogic(scl_io); -- sense
----
